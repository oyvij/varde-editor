Varde — the walking skeleton

Every feature is one slice: a gesture becomes an Event, one on_* handler in lib.rs answers it (usually through a pure area module), writes the carrier State and returns the outside work as Effect data, which main.rs carries out before ui.rs draws the new State.

Press play. The orbs are data: blue for an Event, gold for an Effect, green for the new State, violet for an answer coming back from the outside world. Gates flash red when a handler declines and pass the Event on, and green when one answers.

Each part below was tested by adding a toy :ping feature to a scratch copy, removing that part and building again. The table after the cards shows what removing each part costs.

pub enum Event { …, Ping }                 // lib.rs:274  the request
pub struct State { …, pub pings: usize }   // lib.rs:965  the carrier field
impl Default for State { … pings: 0 }      // lib.rs:1184 the compiler rejects a missing field
pub enum Effect { … }                      // lib.rs:730  outside work, as data

      
src/lib.rs — the slice
fn on_ping(_state: &State, mut next: State, event: Event, wheeled: bool) -> Answered {
    let effects = match event {
        Event::Ping => {
            next.pings += 1;                 // usually area::verb(&mut next, …)
            vec![Effect::Notify("pinged")]
        }
        other => return Err((next, other)),  // not ours: decline
    };
    Ok(settle(next, effects, wheeled))
}

      
src/lib.rs — registration in a route_* chain
// e.g. route_activate, lib.rs:2181
let declined = match on_ping(state, declined.0, declined.1, wheeled) {
    Ok(answer) => return Ok(answer),
    Err(declined) => declined,
};
Without it the build fails: function `on_ping` is never used. #![deny(dead_code)] enforces the registration.

Composition a chain of responsibility, three levels deep

    
route → section_input / editing / workspace → nine route_* → 61 on_* handlers. Every level returns Answered = Result<(State, Vec<Effect>), (State, Event)>: Ok answers the Event, Err hands it to the next link. The runtime has the same shape: perform → perform_terminal / session / files / jobs, mirrored by cucumber's apply → applied_to_*. Slices also call each other through the same entry point: a handler can call update again with another event (lib.rs:3896), and an Effect can come back later as a new Event through the queue.

Navigation the grep keys that connect the layers

    

      
Event::Foo
Produced in keys/mouse/main, matched in an on_* arm, sent in tests/cucumber.rs.

      
Effect::Foo
Emitted by lib or debug/lsp/reading/…, carried out in main.rs perform_* and cucumber.rs applied_to_*.

      
next.foo / state.foo
Only update writes a State field, except facts the edge sets in tell_core. ui.rs reads it.

      
"cmd" => · CHEATSHEET
Every :command is listed in keys.rs, and every key in CHEATSHEET.

    

  


  

    
Deviations what will trip someone following the recipe

    

      
1 · A new Effect with no executor compiles
A release build drops it silently (main.rs:2811). Confirmed in a scratch build. See the third tab.

      
2 · A new Event with no handler compiles
It then panics on the first event (lib.rs:1662). Routing is by declining, so the compiler can't catch a missing arm. See the second tab.

      
3 · Event::AddComment is test-only
Defined at lib.rs:322 with an arm at lib.rs:2761, but only tests/cucumber.rs:3035 ever sends it. The product never does.

      
4 · Numbered handler names
on_key_2…6, on_editor_key_2…6 and on_activate_2…4 say nothing about what they own. Find a handler by grepping its Event:: instead.

      
5 · Area modules take &mut State
debug.rs, lsp.rs and risk.rs take &mut State rather than plain data, so a change to State reaches into those modules too.

      
6 · lib.rs holds every area's handlers
About 7,600 lines. A feature always touches lib.rs, even when its logic lives in an area module.
